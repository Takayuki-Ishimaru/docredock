# AIドキュメント質問応答における形式別トークン効率検証

- 検証日: 2026-08-25
- 対象形式: Markdown（`.md`）、Markdown + DRMD sidecar（`.md + .drmd`）、Excel（`.xlsx`）
- 検証対象: 経費精算システム設計書（検証用）
- 実行環境: ローカルCodex CLI 0.149.0-alpha.4.3
- 試行回数: 初回検証は各形式1回、小型モデル追加検証は各形式3回

## 1. 結論

AIがドキュメントの内容へ質問回答する用途では、今回の一般的なローカルエージェント環境において、**Markdown単体が最もトークン効率と処理速度に優れていた**。

- テキスト情報だけを質問する場合: `.md` が最適
- 画像内情報も含めて高精度に回答する場合: `.md + .drmd` が最もバランス良好
- 数式、セル、シート構造、図形、レイアウトを維持した編集が必要な場合: `.xlsx` を正本として利用
- Excel単体は全問正答したが、質問回答用途のトークン効率は3形式中で最も低かった

前回の検証で「Excelが最も効率的」と見えた結果は、Excel側のみ関連セルを抽出した状態に近く、Markdown側の全体読み取りと条件が揃っていなかったためである。今回の実測結果に基づき、その結論は撤回する。

## 2. 検証対象

架空の経費精算システム設計書を、同一内容の3形式で使用した。

- Markdown（`.md`）
- Markdown + DRMD sidecar（`.md + .drmd`）
- 元Excel（`.xlsx`）

`.md + .drmd` 条件では、Markdown本文に加えてDRMD sidecar内の原画像などを参照可能とした。検証入力と生成出力そのものは、公開物を利用に必要な最小構成へ絞る方針からリポジトリに同梱していない。測定方法、質問、集計値、解釈は再検討できるよう本書に残している。

## 3. 測定条件

形式以外の差を抑えるため、次の条件を揃えた。

- 3ケースをそれぞれ独立した一時セッションで実行
- 同一の12問を使用
- 同一の構造化JSON回答スキーマを使用
- 同じデフォルトモデルおよびCodex設定を使用
- Web検索は禁止
- ファイル変更は禁止
- 事前変換、専用インデックス、検索用要約、関連セル指定は不使用
- 読み取り方法は、一般的な作業と同様にエージェント自身が選択
- 各条件で指定された入力以外は回答根拠として使用しない
- 判断できない情報は推測せず「判定不能」と回答

トークン数はCodex CLIの完了イベントに記録された実測値を使用した。ここでの入力トークンは、元ファイルの文字数ではなく、システム指示、ツール結果、会話履歴などが各モデル呼び出しへ再投入された分を含む累積値である。

### 空実行ベースライン

ファイルを読ませず「OK」とだけ回答させた実行では、次の使用量だった。

- 入力トークン: 16,022
- うちcached input: 9,984
- 出力トークン: 5

結果表の「ベースライン差引後入力」は、各ケースの入力トークンから16,022を差し引いた参考値である。

2. IF-05の送信元、送信先、Timeout、Retry、失敗時処理
3. TR-09の遷移元、イベント、ガード、遷移先、副作用
4. TX-01の書き込み対象とHTTP応答後のイベント配送
5. BR-01の金額閾値と承認経路
6. F-06の必須条件、最大サイズ、エラーコード、メッセージ、表示位置
7. API-01のMethod、Path、応答、Idempotency-Key制約
8. TC-009の入力、経路、HTTP、最終状態、関連設計
9. NFR-AVL-02のRTO、RPO、測定方法、実現手段、合意状態
10. ISSUE-03の論点、作業、Owner、期限、Status
11. outbox_event.statusの候補値とretry_count上限
12. IMG-02の画像内だけに存在する文字列

Q12の正解は `OCR-JP-20260823-017` であり、Markdown本文には文字列として収録されていない。

| 入力形式 | 入力トークン | cached input | 非cached input | 出力トークン | 合計 | ベースライン差引後入力 | 正答数 | 所要時間 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| `.md` | 85,915 | 48,640 | 37,275 | 1,657 | 87,572 | 69,893 | 11/12 | 34.9秒 |
| `.md + .drmd` | 136,555 | 98,304 | 38,251 | 2,391 | 138,946 | 120,533 | 12/12 | 60.0秒 |
| `.xlsx` | 332,022 | 289,024 | 42,998 | 7,361 | 339,383 | 316,000 | 12/12 | 155.5秒 |

合計は入力トークンと出力トークンの和である。cached inputも使用量には含めているが、料金を比較する場合は利用モデルのキャッシュ料金を別途適用する必要がある。本検証では金額換算を行っていない。

## 6. 相対比較

### Excelとの比較

- `.md` はExcelより入力トークンが **74.1%少ない**
- `.md + .drmd` はExcelより入力トークンが **58.9%少ない**
- Excelは `.md` の **約3.86倍** の入力トークンを使用
- Excelは `.md` の **約4.45倍** の処理時間を要した

### MarkdownとDRMDの比較

- `.md + .drmd` は `.md` より入力トークンが **58.9%多い**
- その増加により、Markdown本文では取得できなかった画像内限定情報を回答できた
- テキスト情報11問については、両形式とも全問正答した

## 7. 回答精度の評価

### Markdown単体

- 総合精度: 11/12（91.7%）
- テキスト情報のみ: 11/11（100%）
- 誤答・欠落: Q12のみ
- Q12は画像内だけにある文字列であるため、「判定不能」という回答は入力形式から見て妥当

通常の仕様、表、API、状態遷移、非機能要件など、テキスト化された内容への質問では精度上の問題は確認されなかった。

### Markdown + DRMD

- 総合精度: 12/12（100%）
- Markdown本文からテキスト情報を取得
- DRMD sidecar内の原画像を確認し、画像内限定文字列も取得

テキスト中心の効率を維持しつつ、画像などMarkdown単体で失われる情報を補えるため、今回の用途では最もバランスがよかった。

### Excel単体

- 総合精度: 12/12（100%）
- セル値、複数シート、表、埋め込み画像を確認できた
- 一方で、スプレッドシート用手順の読み込み、シート範囲の探索、セル検査、画像確認などの処理が必要となり、累積トークンと処理時間が大幅に増えた

## 8. Excelのトークン消費が大きくなった理由

Excelファイルのバイナリサイズが小さいことは、そのままAIへの入力トークンが少ないことを意味しない。一般的なコーディングエージェントはExcelのOOXMLバイト列を直接理解するのではなく、次の処理を介して内容を取得する。

1. ワークブックとシート構造を認識する
2. 関連しそうなシートやセル範囲を探索する
3. 必要なセル値、数式、表、オブジェクトを抽出する
4. 抽出結果をモデルのコンテキストへ戻す
5. 必要に応じて別範囲や埋め込み画像を追加確認する
6. それまでの会話・ツール結果を含めてモデルを再実行する

そのため、最終回答に必要な情報量が同じでも、Excelではツール呼び出しとコンテキスト再投入が増え、累積入力トークンが大きくなる。

今回のExcel回答では、一般的なスプレッドシート作業環境の指示に従った範囲指定や出典情報も付与された。このオーバーヘッドは、特別な最適化をしない通常作業の一部として測定値に含めた。

## 9. 用途別の推奨

| 主な用途 | 推奨形式 | 理由 |
| --- | --- | --- |
| AIによる内容検索、要約、質問回答 | `.md` | 最小のトークンと最短時間で、テキスト情報は全問正答 |
| テキストに加えて画像・原資料も参照 | `.md + .drmd` | 全問正答し、Excelより大幅に少ないトークン |
| 数式、セル、シート、図形、書式を保持した編集 | `.xlsx` | 構造的な編集対象として元形式が必要 |
| 人間がExcelを編集し、AIは内容を質問回答 | Excelを正本、`.md + .drmd` をAI参照用 | 正本性とAI効率を分離できる |

実務上は、Excelを破棄してMarkdownだけに置き換えるのではなく、**Excelを正本として保持し、AI参照用に `.md` または `.md + .drmd` を併設する構成**が適している。

## 10. 制約と解釈上の注意

- 初回検証は各形式1回である。小型モデル追加検証は各形式3回とし、ばらつきと完了率を別途評価した
- 結果はローカルCodexの一般的なエージェント作業に対するものであり、すべてのAI製品にそのまま当てはまるとは限らない
- ファイルのサイズ、シート数、画像数、質問内容、読み取りツールにより差は変動する
- 事前インデックス、RAG、関連範囲指定などを導入すれば、全形式で使用量を削減できる可能性があるが、今回は「特別な最適化なし」という条件から除外した
- APIへExcelを直接添付する環境では、サービス側のスプレッドシート変換方法によって結果が異なる
- OpenAIのFile inputsでは、スプレッドシートに専用の拡張処理が行われる一方、非PDFファイル内の埋め込み画像やグラフはモデルコンテキストへ抽出されないため、本検証のQ12と同じ結果になるとは限らない

参考:

- [OpenAI File inputs](https://developers.openai.com/api/docs/guides/file-inputs)
- [OpenAI Responses API — Create a model response](https://developers.openai.com/api/reference/cli/resources/responses/methods/create)

## 11. 最終判断

質問回答を中心とする通常のAI作業では、次の優先順位とする。

1. **`.md`** — テキスト中心なら最も効率的
2. **`.md + .drmd`** — 画像・原資料を含む完全性が必要なら最適
3. **`.xlsx`** — 編集上の正本として必要だが、質問回答のトークン効率は低い

したがって、DRMDの運用方針としては、Excelなどの元文書を正本として保持しながら、AIへの質問回答にはMarkdown投影を優先し、画像・原資料が必要な場合だけDRMD sidecarを併用するのが合理的である。

## 12. 小型モデル追加検証

### 12.1 目的とモデル

「Markdownへの変換で情報量が軽くなれば、低性能なAIでも回答精度または完了率が改善するか」を確認するため、同じ12問を小型モデルで再実行した。

- モデル: `gpt-5.4-mini`
- 試行回数: 各形式3回、合計9回
- Excelの実行上限: 1試行12分
- その他の条件: 初回検証と同一
- 空実行ベースライン: 入力13,752、cached input 4,480、出力28、6.2秒

OpenAIは `gpt-5.4-mini` を高速・高効率なminiモデルとして位置づけている。ただしコンテキストウィンドウは400,000トークンであるため、この追加検証は**低性能・低コスト側のモデルにおける挙動検証**であり、8Kや16Kなどの短いネイティブコンテキスト上限を再現した検証ではない。

- [OpenAI GPT-5.4 Mini](https://developers.openai.com/api/docs/models/gpt-5.4-mini)

### 12.3 形式別集計

入力・出力・合計は完了試行の平均である。時間はタイムアウトを12分として含めた全3試行の平均である。

| 形式 | 完了率 | 平均入力 | 入力中央値 | 平均非cached入力 | 平均出力 | 平均合計 | 完了時精度 | 完了調整後精度 | 平均時間 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| `.md` | 3/3（100%） | 249,177 | 131,061 | 39,684 | 11,218 | 260,395 | 91.7% | 91.7% | 155.9秒 |
| `.md + .drmd` | 3/3（100%） | 484,859 | 405,701 | 98,555 | 11,577 | 496,437 | 100% | 100% | 164.1秒 |
| `.xlsx` | 2/3（66.7%） | 2,756,080 | 2,756,080 | 205,296 | 45,176 | 2,801,256 | 100% | 66.7% | 688.5秒 |

「完了調整後精度」は、タイムアウト試行を正答0として全試行・全36問を分母にした参考値である。Excelの完了時精度は高いが、12分以内に回答を返せない試行を含めると実用上の成功率が低下する。

### 12.4 相対比較

完了試行の平均入力トークンで比較すると、次の結果になった。

- `.md` はExcelより **91.0%少ない**
- `.md + .drmd` はExcelより **82.4%少ない**
- Excelは `.md` の **約11.1倍**
- Excelは `.md + .drmd` の **約5.68倍**
- `.md + .drmd` は `.md` の **約1.95倍**

初回のデフォルトモデル1試行と比較すると、小型モデルの平均入力は次のように増加した。

| 形式 | デフォルトモデル入力 | 小型モデル平均入力 | 倍率 |
| --- | ---: | ---: | ---: |
| `.md` | 85,915 | 249,177 | 2.90倍 |
| `.md + .drmd` | 136,555 | 484,859 | 3.55倍 |
| `.xlsx` | 332,022 | 2,756,080 | 8.30倍 |

この増加は、小型モデルが関連情報の探索、範囲確認、根拠確認を繰り返し、ツール結果と会話履歴がモデルコンテキストへ再投入されたためである。ファイル自体のテキスト量が少なくても、エージェントの探索が収束しなければ累積トークンは増える。

### 12.5 精度と仮説の評価

追加検証の結果、仮説は次の意味で支持された。

- Markdownは3回すべて完了し、テキスト11問は毎回全問正答した
- DRMDは3回すべて完了し、画像問題を含めて毎回12/12正答した
- Excelは完了した2回では12/12正答したが、1回は12分以内に回答できなかった
- 小型モデルにとって、Markdown/DRMDはExcelより回答完了までの経路が短く、実用上の信頼性が高かった
- 特にDRMDは、小型モデルでも画像情報を失わず、3/3で完全回答できた

一方、**トークンが少ない形式を使えば、小型モデルの累積トークンも必ず少なくなるわけではない**。小型モデルは高性能モデルより探索反復が増え、3形式すべてで平均入力トークンが増加した。

したがって今回確認できた効果は、「小型モデルの正答率を100%よりさらに高くする」ことではなく、次の点にある。

1. テキスト化された情報を小型モデルでも安定して取得できる
2. Excel直接処理で発生する長時間探索やタイムアウトを回避しやすい
3. DRMDを併用すれば、画像情報を保持したまま完了率100%を維持できる
4. Excelに比べ、累積入力トークンと待ち時間を大幅に抑えられる

### 12.6 追加検証後の判断

低性能・低コスト側のAIを利用する場合、推奨順位は初回検証より明確になった。

1. **テキスト質問は `.md`**
   最小の平均トークンで、テキスト質問は全試行100%正答した。

2. **画像を含む質問は `.md + .drmd`**
   全試行・全12問に正答し、Excelより平均入力を82.4%削減した。

3. **Excel直接質問は避ける**
   完了時の精度は高いが、平均入力約276万トークン、平均約11分28秒、完了率66.7%となり、小型モデルでは実用性が低い。

結論として、**Markdown/DRMD化は小型モデルの知能そのものを高めるのではなく、モデルが回答へ到達するための探索負荷を下げ、完了率と実用上の安定性を改善する**。短コンテキストモデルでの効果を厳密に確認するには、別途ネイティブなコンテキスト上限を固定できるAPI環境での検証が必要である。
